# Architecture

## Overview

This repository carries no application business logic. Its architecture is that of the **speckit** Spec-Driven Development (SDD) substrate: a set of bash scripts, markdown templates, and workflow definitions that guide an AI agent (or a human) through a structured feature-delivery cycle.

---

## Component Map

### `.specify/scripts/bash/` — Core execution scripts

Six bash scripts form the runtime of speckit:

- **`common.sh`** — Shared functions imported by all other scripts. Locates the project root (walking up from cwd until `.specify/` is found), resolves the `SPECIFY_INIT_DIR` override for monorepo use, and provides logging/JSON helpers.
- **`check-prerequisites.sh`** — Validates that the speckit substrate is intact for the current feature branch. Checks for required files, outputs paths, and can list available spec artifacts. This is the verification gate.
- **`create-new-feature.sh`** — Scaffolds a new feature directory under `specs/` with a sequential (or timestamp-based) number prefix. Accepts `--short-name`, `--number`, `--dry-run`, and `--json` flags.
- **`setup-plan.sh`** — Populates `specs/<feature>/plan.md` from the plan template, wiring in branch and date metadata.
- **`setup-tasks.sh`** — Populates `specs/<feature>/tasks.md` from the tasks template.
- **`resolve-template.sh`** — Substitutes template variables (`$ARGUMENTS`, dates, branch names) into a given markdown template and emits the result to stdout.

### `.specify/templates/` — Markdown templates

Five templates define the shape of each SDD artifact:

| File | Produces |
|---|---|
| `spec-template.md` | `specs/<feature>/spec.md` — user stories, acceptance scenarios, functional requirements, success criteria |
| `plan-template.md` | `specs/<feature>/plan.md` — technical context, constitution check, phase-by-phase implementation plan |
| `tasks-template.md` | `specs/<feature>/tasks.md` — ordered task list with acceptance criteria |
| `checklist-template.md` | Ad-hoc review checklists |
| `constitution-template.md` | `.specify/memory/constitution.md` — blank constitution scaffold for recording core engineering principles |

### `.specify/workflows/` — Workflow definitions

- **`speckit/workflow.yml`** — Defines the `speckit` Full SDD Cycle: `specify → review-spec → plan → review-plan → tasks → implement`. Each step dispatches a `speckit.*` command to a configured AI integration (claude, copilot, gemini, etc.). Human review gates (`type: gate`) sit between specify→plan and plan→tasks, preventing automation from proceeding without approval.
- **`workflow-registry.json`** — Index of installed workflows with version and installation metadata.

### `.specify/memory/constitution.md` — Project constitution

A markdown file that records the project's core engineering principles (e.g. "library-first", "TDD mandatory"). At present this file contains only the blank template; it is intended to be filled in by the project team. The constitution is referenced by the plan template's "Constitution Check" gate before implementation begins.

### `.mcp.json` — MCP server configuration

Registers a Playwright MCP server (`npx @playwright/mcp@latest --headless --isolated`) for use by the Claude agent. This enables browser automation during implementation steps without requiring a separate Playwright install in the repo.

## Data Flow: Full SDD Cycle

```
User describes a feature
        │
        ▼
[specify]  AI generates spec.md from spec-template.md
        │
        ▼
[gate]   Human reviews spec — approve or abort
        │
        ▼
[plan]   AI generates plan.md + research.md + data-model.md from plan-template.md
        │
        ▼
[gate]   Human reviews plan — approve or abort
        │
        ▼
[tasks]  AI generates tasks.md from tasks-template.md
        │
        ▼
[implement]  AI implements tasks, referencing spec + plan + tasks artifacts
```

All artifacts land under `specs/<NNN-feature-name>/` in the project root (created by `create-new-feature.sh`). The feature number `NNN` is auto-assigned sequentially, preventing collisions across concurrent branches.

## Cross-Cutting Concerns

**Integration dispatch**: The workflow's `integration` input (default: `"auto"`) determines which AI backend runs each `speckit.*` command. This is resolved at runtime by the speckit engine — the scripts themselves are integration-agnostic.

**Monorepo support**: `SPECIFY_INIT_DIR` can be set to a subdirectory so speckit commands operate on a member project without `cd`-ing into it. `common.sh`'s `resolve_specify_init_dir()` validates and normalizes this path strictly (no silent fallback).

**No build system**: The substrate is pure bash. No package manager, compiler, or test runner is required.

---

## Notable Design Decisions

**Human gates between phases**: The workflow inserts mandatory human review gates between specify→plan and plan→tasks. This prevents an AI from silently cascading a misunderstood spec into a full implementation plan. The alternative (fully automated pipeline) was rejected to preserve human control at the highest-leverage decision points.

**Template-driven artifacts**: All SDD documents are produced from versioned markdown templates rather than being generated free-form. This ensures structural consistency across features and integrations, and makes the format auditable without running any code.

**`speckit_version: ">=0.8.5"` requirement**: The workflow declares a minimum speckit engine version. Prior versions treated `integration: "auto"` as a literal integration key and would fail at dispatch. The version pin makes this constraint explicit rather than relying on runtime discovery.
